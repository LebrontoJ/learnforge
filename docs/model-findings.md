# 首轮真实模型验收发现

本轮使用 Gemini 3.1 Flash-Lite、固定开发者资料和独立浏览器规则，20/20 案例已执行完成。案例总数、完成状态及指标以 `evaluation-model.md` 为准。供应商 HTTP 503 与代码检查失败分别记录，不能混为内容正确率。

## 已观察到的问题

1. **控件契约不足以稳定约束输出。** 模型经常使用 `id="run"` 等属性，而浏览器协议要求 `data-testid="run"`。部分修复版本仍遗漏按钮的测试标识。现有生成提示对按钮属性的表述还可以更明确，并提供完整的受限控件骨架；这是平台提示与模型遵循度共同造成的集成问题。
2. **运行通过不等于交互通过。** `binary-1` 与 `binary-2` 首版可以加载，因控件协议问题不能完成操作；真实模型读取失败证据后产生新的 HTML，复验通过。初始代码和报告均保留，不能用修复版替代首版证据。
3. **修复上限确实会交付失败。** `binary-3` 在两轮修改后仍缺少必要的按钮标识，最终保持失败，不通过修改断言、自动放宽检查或套回固定模板获取通过。
4. **无法执行断言时，不推断算法算错。** 控件定位失败会使该案例的技术规则检查无法完成；其原因是接口不兼容，不能据此声称二分查找计算结果错误。
5. **模型服务可用性会增加成本。** 本轮出现明确的 HTTP 503，部分请求经过有限重试才成功；报告的调用数包含失败 HTTP 尝试。没有 Token 用量的失败请求不伪造费用为零。

核对已完成的前四个案例的原 HTML 后，未发现 `<form>`；这些案例的已确认根因是控件标识缺失，不能将其归咎于清洗表单。表单等不支持的结构仍属于预览兼容性边界，但应根据具体产物另行判断。

## 最终结果与失败归因

- 运行检查：20/20；首次行为：0/16；修复后行为：12/16；独立技术规则：8/16；修复回归：0/16。
- 12/20 最终产物通过平台工程检查，其中 4 个普通讲稿不包含独立语义验证。
- 控件标识问题：binary-3、binary-4、binary-5、lru-9。lru-9 已保留首版与一个修复版，后续调用预算耗尽，不能误写成没有任何产物。
- lru-6：输出顺序与接口约定相反，得到 C、A，要求为最旧到最新的 A、C；这不直接证明淘汰成员错误。
- lru-10：默认演示可以操作，但缺少供边界输入使用的 data 控件。
- rate-11：将序列输入实现成数值输入，无法填入 0,10,20。
- rate-14：单样本返回的 JSON 是 null，协议要求带 rate:null 的对象；属于结果结构不兼容。
- HTTP 尝试 100 次，其中 35 次被服务拒绝；已报告 Token 147,589，费用未知。

这些失败主要涉及生成控件与状态输出契约，不能将比例泛化为技术知识正确率。资料不足和不支持能力两个案例也只通过基础工程检查，尚不能证明其内容级降级提示完全满足 PRD。

## 本轮保持不变的条件

没有因为结果不好修改独立参考答案、测试选择器或生成代码。A 与 B 共享同一份教学规格和初始代码；B 仅增加浏览器反馈与至多两轮真实模型修复。调用预算包含服务错误重试，触及预算时保留部分结果。

## 后续改进建议

- 为交互节点提供完整、明确的属性契约与最小 HTML 骨架，在生成后进行结构检查，再进入浏览器；仍保留原始输出及结构修正记录。
- 将“控件缺失导致无法执行技术断言”与“执行后数值不符合参考实现”分开展示，避免误归因。
- 补充讲稿目标、示例、误区、总结和引用支持的独立内容审查。当前浏览器技术规则只覆盖简化演示，不能证明整篇讲稿正确或内容完整。
- 完成真实搜索和独立人工审查；设置开发期间未查看答案的保留集后，再做可推广的质量比较。

这些是基于验收证据的后续项，本轮没有在测试中途改变生成契约来制造更高通过率。
